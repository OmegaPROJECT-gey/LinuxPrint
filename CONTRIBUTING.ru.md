# Участие в разработке LinuxPrinterG

Спасибо, что хотите внести вклад. Здесь описан весь процесс: окружение,
проверки, стиль, переводы и то, как изменение попадает в основную ветку.

Внося вклад, вы соглашаетесь, что ваш код распространяется на условиях
[MIT-лицензии](LICENSE) проекта — такой же, как у остального кода.

## Перед началом

1. Прочитайте [PHILOSOPHY.ru.md](PHILOSOPHY.ru.md). Фича, противоречащая ей,

2. Прочитайте [ARCHITECTURE.ru.md](ARCHITECTURE.ru.md) — граница между

   issue, если планируете что-то крупное.

## Окружение

* **Rust 1.85+** (workspace на edition 2024).
* Для UI-крейта: dev-пакеты GTK4 ≥ 4.14 и libadwaita ≥ 1.5
  (`libgtk-4-dev` + `libadwaita-1-dev` в Debian/Ubuntu, `gtk4-devel` +
  `libadwaita-devel` в Fedora, `gtk4` + `libadwaita` в Arch).
* Утилиты, которые нужны тестам: `cups-client`, `sane-utils`, `poppler-utils`;
  опционально `tesseract-ocr` и LibreOffice.
* В песочнице без root и без dev-пакетов GTK воспользуйтесь
  `scripts/setup-fedora-dev-prefix.sh` и экспортируйте `PKG_CONFIG_PATH` /
  `RUSTFLAGS`, как описано в README.

## Проверки, которые обязаны пройти

Запускайте их локально — CI выполняет ровно те же команды:

```bash
cargo fmt --all -- --check        # или: make fmt-check
cargo clippy --workspace --all-targets -- -D warnings   # или: make clippy
cargo test --workspace            # или: make test
```

Интеграционные тесты, вызывающие настоящие утилиты, включаются явно:

```bash
make test-int     # cargo test -p linuxprinterg-core -- --ignored --test-threads=1
```

Остальные полезные таргеты: `make build`, `make run`, `make release`,
`make fmt` (переформатирование), `make po` и `make po-build` (переводы),
`make deb` / `make rpm` / `make packages` (упаковка).

## Стиль

* Форматирование целиком берёт на себя `rustfmt` с `rustfmt.toml` из
  репозитория (edition 2024, `max_width = 100`) — пробелы не обсуждаются на
  ревью.
* Предупреждения clippy считаются ошибками; если линтер действительно
  неправ, подавите линту через `allow` с комментарием, **почему** это
  необходимо, — никогда молча.
* **Комментарии в коде пишутся на русском языке.** Это установившаяся
  конвенция репозитория: doc-комментарии модулей (`//!`), документация `///`
  и строчные комментарии — по-русски; идентификаторы остаются английскими.
* Doc-комментарии объясняют замысел и ограничения, а не синтаксис.
* Соблюдайте разделение: разбор данных, форматы файлов и вызовы процессов —
  в `linuxprinterg-core`; всё, что связано с GTK, — в UI-крейте. Логика ядра
  обязана оставаться тестируемой без display-сервера.

## Переводы (i18n)

* Словарь RU/EN лежит в `crates/linuxprinterg-core/src/i18n.rs`. Новая
  пользовательская строка добавляется **дважды**: в запись словаря
  (`key → (en, ru)`) **и** в массив `ALL_KEYS`. Тесты
  (`cargo test -p linuxprinterg-core`) упадут, если чего-то из этого не
  хватает или если в локалях разошлось количество плейсхолдеров.
* uk/de/fr — gettext-overlay. Изменив словарь, выполните `make po`: он
  перегенерирует `po/linuxprinterg.pot` и допишет недостающие ключи в
  `po/uk.po`, `po/de.po`, `po/fr.po`. Новые `msgstr` заполните сами или
  оставьте пустыми: пустая запись или запись с `#, fuzzy` на рантайме
  откатывается на английский.
* `make po-build` компилирует `.po` в
  `locale/<ll>/LC_MESSAGES/linuxprinterg.mo`.
* Не меняйте `msgid` (псевдоключ) без правки словаря — `.po` выводятся из
  него.

## Pull request

1. Сделайте форк, создайте ветку, держите коммиты сфокусированными (одна
   проблема — один PR).
2. Убедитесь, что локально проходят `fmt-check`, `clippy` и `test`.
3. Опишите, **что** изменилось и **почему**; для изменений UI приложите
   скриншот, для новых парсеров — укажите добавленные фикстуры.
4. Обновите документы, к которым прикоснулись: README — для видимых
   пользователю фич, CHANGELOG.md в разделе `[Unreleased]`, чекбоксы
   ROADMAP.md, когда пункт дорожной карты выполнен. Каждый документ существует
   в английской и русской версии — правьте обе части пары в одном PR.
5. CI прогонит fmt · clippy · тесты · release-сборку · `.deb`/`.rpm` ·
   Flatpak — будьте готовы исправить то, что он найдёт.

## Issues

Заводите issue, когда нашли баг или хотите обсудить фичу. Полезный issue
содержит: версию приложения, дистрибутив и рабочий стол (Wayland/X11), модель
принтера или сканера, шаги воспроизведения, ожидаемое и фактическое поведение
и хвост `~/.local/state/linuxprinterg/logs/linuxprinterg.log` (при
необходимости поднимите уровень логов в настройках). В запросах фич
описывайте реальную проблему, а не только предложенное решение.

Публичные issues для проблем безопасности **не предназначены** — см.
[SECURITY.ru.md](SECURITY.ru.md).
