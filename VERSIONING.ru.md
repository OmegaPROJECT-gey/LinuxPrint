# Версионирование

LinuxPrinterG следует **[Semantic Versioning 2.0.0](https://semver.org/lang/ru/spec/v2.0.0.html)**:
схема `MAJOR.MINOR.PATCH` с метками pre-release. Здесь объяснено, что каждый
сегмент означает именно для этого проекта.

---

## Источник истины

Версия хранится **в одном месте**: `[workspace.package] version` в корневом
`Cargo.toml` (сейчас `0.1.0`). Makefile, скрипты упаковки, CI и манифест
Flatpak читают её оттуда — ни один файл не содержит версию, вписанную руками.
Если документы и `Cargo.toml` разошлись — прав `Cargo.toml`.

Текущий релиз всегда описан в [CHANGELOG.ru.md](CHANGELOG.ru.md) в
собственном разделе.

## Что такое API

Для проекта, похожего на библиотеку, «публичный API» — это **публичный
интерфейс крейта `linuxprinterg-core`**: экспортируемые функции, структуры и
перечисления, их поля и смысл, а также поведение, на которое опирается
документированный код.

* Изменение, ломающее вызывающий код, — удаление или переименование
  публичного элемента, изменение сигнатуры, изменение того, что парсер
  принимает или возвращает, — считается **ломающим** изменением.
* UI-крейт — конечный продукт, а не библиотека: его внутренности меняются
  свободно, но всё, что меняет видимое пользователю поведение (значения по
  умолчанию, форматы файлов, структура журнала), трактуется как изменение API
  и проходит по тем же правилам.

## Правила до 1.0

Пока версия `0.x`:

* **MINOR** может содержать ломающие изменения — это контракт SemVer для
  `0.y.z`;
* **PATCH** — никогда: только исправления, переводы, упаковка и производительность;
* после объявления `1.0.0` ломающие изменения переезжают в **MAJOR**, а
  поведение `0.x` остаётся в истории.

## Номера патчей по календарю

Номера патчей выдаются в порядке релизов: каждый датированный релиз прибавляет
единицу к сегменту `PATCH`, какой бы маленький он ни был. Даты релизов
зафиксированы в [CHANGELOG.ru.md](CHANGELOG.ru.md), поэтому номер версии и
журнал изменений живут на одной шкале — по одному числу всегда видно, какая
из двух сборок новее, не сверяя метки времени.

## Метки pre-release

Работа, ещё не готовая для широкой аудитории, помечается идентификаторами
pre-release по SemVer, от старых к новым:

| Метка | Значение |
|---|---|
| `0.2.0-alpha.1` | ранняя сборка, API и поведение ещё могут меняться |
| `0.2.0-beta.1` | функционал собран, идёт поиск регрессий |
| `0.2.0-rc.1` | кандидат на релиз, принимаются только исправления |

Порядок `alpha.N < beta.N < rc.N < final` задан самим SemVer (`alpha`
сортируется раньше `beta`, идентификаторы с дефисом — раньше финальной
версии). Менеджеры пакетов не ставят pre-release поверх финальной версии,
если пользователь явно не выбрал этот канал.

## Теги и артефакты

* Релиз помечается annotated-тегом **`vX.Y.Z`** (например `v0.1.0`) — ведущая
  `v` принадлежит тегу, а не версии.
* В момент отправки тега тег, версия из `Cargo.toml` и раздел CHANGELOG
  обязаны совпадать; CI по этому же коммиту собирает `.deb`/`.rpm` с этим
  именем (`linuxprinterg_X.Y.Z_amd64.deb`,
  `linuxprinterg-X.Y.Z-1.x86_64.rpm`) и бандл Flatpak.
* Pre-release теги несут метку: `v0.2.0-rc.1`.
* Порты исправлений, если они когда-нибудь понадобятся, живут на отдельной
  ветке со своим суффиксом и не публикуются новее основной линии.

## Связь с журналом изменений

Каждый раздел релиза в [CHANGELOG.ru.md](CHANGELOG.ru.md) назван тем же
`X.Y.Z` и той датой, когда поставлен тег. Всё, заметное пользователю, сначала
попадает в `[Unreleased]` и переносится в раздел релиза при постановке тега —
поэтому диф между двумя тегами отвечает сразу на два вопроса: «что
изменилось» и «почему число сдвинулось».
